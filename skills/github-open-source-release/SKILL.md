# GitHub 开源发布

交付可访问的公开仓库、可核验的提交与图片说明；用户要求新版本时，再交付对应 Release。使用现有 GitHub CLI、连接器或已登录的浏览器，不新增自动发布脚本。

维护 WPS 一键排版项目时，先读 [项目参考](references/wps-local-formatter.md)；其他项目沿用下述流程，不套用 WPS 的平台或命令。

若目标仓库携带同名 skill，优先读取仓库版本；维护该 skill 后同步环境中已安装的副本，安装目录按当前环境确定，公开文件不写个人绝对路径。

## 工作流程

1. **定位项目与授权。** 从用户消息、项目内容和 Git 状态核定目标目录、仓库、公开范围与完成条件；当前目录不能单独证明用户指定的项目。读取适用的项目说明，检查已有改动、remote、默认分支、仓库可见性和现有 Release。沿用会话中已有的开源、push 或发布授权，不反复确认；缺少关键目标或公开授权时，先完成可独立进行的准备，再只询问缺失项。删除仓库、改写已推送历史等额外操作需要相应授权。

2. **准备真实示例与说明。** 优先使用合成数据，在实际程序中展示主要入口、操作结果和有价值的前后对比。先读取界面状态，保护用户文档与未保存工作；不为截图改写用户配置或重启含未保存工作的应用。检查图片内容及元数据，去除姓名、案件、文档正文、令牌和个人路径。保留能解释真实产品的界面，不用生成图伪造运行结果；模拟界面须标明。把通过检查的图片放入公开的图片目录，用相对路径和有意义的替代文字嵌入 README，并写清安装、最短使用步骤及验证边界。

3. **审查将公开的内容。** 检查明确列出的文件和差异，以及首次公开时准备推送的可达提交历史。不得上传个人文档、用户配置、凭据、字体或其他未经许可的依赖；ignored 文件及本地 evidence 不因“目录中存在”而进入发布包。发现秘密时先停止相关公开动作并报告，不能只删除当前文件就声称历史安全。保留已有许可证；新增许可证须与源码权属和第三方许可兼容，同时保留必要的声明、贡献说明。打包有白名单时同步纳入新增公开图片与可复用 skill，不扩大到整个工作目录。

4. **完成相应验证。** 运行项目已有的相关测试、构建或 CI；局部文档改动重点检查 Markdown 图片和链接能解析、图片尺寸适合阅读、公开文件无敏感内容。保留现有 CI，不为文档改动堆叠产品测试。验证打包改动时检查压缩包内实际文件；源码、自动测试、预览、正式 App、真实文档、设备和在线状态分别说明，不把其中一层替代另一层。

5. **提交并核验远程。** 使用明确路径暂存并审阅 staged diff，避免 `git add .` 或 `git add -A` 带入无关改动。按授权创建或更新公开仓库，提交并推送后读取远程分支 SHA、可见性、README 图片和本次提交的 CI 结果；创建 PR 时按宿主要求附加到当前聊天。异步任务先读回状态；外部调用结果不明时先查远程提交、仓库或 Release 是否已存在，不能直接重复提交或覆盖。

6. **按版本范围发布。** 文档、图片和 skill 的维护可以只更新仓库；用户未要求新的产品版本时，不为了这些变更升级版本、移动旧 tag 或替换历史发布资产。发布新版本时统一源码版本、tag、发布说明及资产名称，确认 tag 指向已验证提交。检查源码包白名单、许可证和公开示例，生成并校验资产哈希；读取远程 Release 的 tag、资产名称与尺寸，核对下载后的哈希及源码包与 tag 内容的一致性。测试版保持预发布标记与已知边界；删除或替换现有 Release 资产须单独核定授权与影响。

## 交付

简短提供仓库、提交、图片示例和已创建的 Release 链接，说明通过的检查及仍未验证或失败的事项。只有远程读回确认后，才声称已开源、已发布或 CI 已通过；任务目标达到即可交付。
